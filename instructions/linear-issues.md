# Linear Issueの作成と管理

> この節は、作業でLinearを利用する場合にのみ適用する。Linearを使わない作業では、Issueの作成・紐付けを要求しない。対象Issueが見つからない、またはLinearに接続できない場合はその状態を明示し、Issue IDを作成・推測して成功扱いしない。

## 基本方針

- Linearは個人開発のIssue管理・進捗管理に使用する。

- GitHub上のコード、ブランチ名、コミット履歴、PRタイトルはLinearに依存させない。

- Linear Issue IDの記載は、GitHub PR本文に限って許可する。

- Linear公式GitHub Integrationを利用し、PRとIssueの関連付けおよびステータス連携を維持する。

- 既存リポジトリの規約・共有指示を尊重し、共通指示と矛盾する場合はリポジトリ側を優先する。Linear Issue IDの公開範囲も、リポジトリ側のルールがあればそれに従う。

## Issue作成・管理

- Issueを作成する際は、常にユーザー自身をAssigneeに指定する。エージェント自身をAssigneeにしない。

- 作成前に既存Issueを検索し、重複を避ける。

- Team・Projectは作業対象と既存Issueから判断する。不明な場合は確認する。

- Issueタイトルは原則日本語とし、簡潔かつ具体的な作業内容を記述する。

- Issue本文には背景・目的・実装方針・完了条件を必要な範囲で記載する。

- Priority、Label、Cycle、Estimateは必要な場合のみ設定する。

- 個人開発に不要な承認フロー、担当者間調整、形式的な進捗報告を要求しない。

- Issueの削除や大規模な変更は事前にユーザーへ確認する。

## Issue作成の積極的な提案

- 開発上の課題、改善案、バグ、技術的負債、将来の実装候補を発見した場合は、積極的にIssue化を提案する。

- ユーザーが新機能や修正について相談した際、実装作業として管理する価値があればIssue作成をリマインドする。

- 調査や設計だけでも、独立した成果物や完了条件がある場合はIssue化を検討する。

- 作業中にスコープ外の問題を発見した場合は、現在の作業を不必要に拡大せず、別Issueとして管理することを提案する。

- 既存Issueで十分に管理できる内容については、新規Issueを作成しない。

- 単なる疑問、軽微なメモ、一時的な試行まで機械的にIssue化しない。

- Issue化を提案する際は、何を管理するためのIssueか、作成するメリットを簡潔に説明する。

- 提案済みのIssueについて、状況が変わっていないのに繰り返しリマインドしない。

- ユーザーがIssue作成を承認した場合は、必要な情報を整理して作成する。

## 親Issue・子Issueの構成

- Issueの可読性、実行可能性、進捗の把握しやすさが向上する場合は、積極的に子Issueを作成してよい。

- 子Issueの作成に毎回の確認は必要ない。ただし、元のIssueの目的やスコープを大きく変更する場合は確認する。

- 親Issueには全体の目的、背景、最終的な完了条件を記載する。

- 子Issueには個別の作業内容、必要な前提条件、検証可能な完了条件を記載する。

- 複数の独立した作業、異なる技術領域、段階的な実装が含まれる場合は、子Issueへの分割を検討する。

- 1つのIssueに大量のチェックリストや複数の独立した完了条件が含まれる場合は、子Issueへの分割を検討する。

- 子Issueは、それ単体を読んで作業に着手できる程度に自己完結させる。

- 親Issueと子Issueに同じ詳細説明を重複させず、情報の責務を分離する。

- 子Issueの粒度は、独立して実装・検証・完了を判断できる単位を目安とする。

- 単純な連続作業や数分で完了する手順を、不必要に子Issueへ分割しない。

- 子Issue間に実際の依存関係がある場合は、Linearの依存関係機能を使用する。

- 親Issueの完了判断では、必要な子Issueの完了状況を確認する。

- 子Issueを作成した場合も、親Issueの全体像が一目で理解できる状態を維持する。

## ステータス管理

- 作業開始時にIssueをIn Progress相当のステータスへ変更する。

- PRの作成・レビュー・マージに伴うステータス更新は、原則としてLinear公式GitHub Integrationに委ねる。

- PRを作成しただけでIssueをCompletedにしない。

- 複数PRが1つのIssueに関連する場合は、すべての必要な変更が完了したことを確認する。

- 公式連携によるステータス更新が機能しない場合は、原因を確認する。

- 必要に応じてLinear APIでステータスを更新するが、公式連携と競合する重複更新を避ける。

- Issueの完了条件が満たされていない場合は、PRがマージ済みでも完了扱いにしない。

- 親Issueは、必要な子Issueが完了し、親Issue自身の完了条件も満たされた場合に完了とする。

## Issueの簡潔性・可読性

* Issueは短く、ひと目で目的と完了条件が把握できるように記述する。

* 背景・目的・実装方針などの定型見出しを機械的に設けない。

* 本文は原則として数行程度に収め、必要な情報が多い場合のみ詳述する。

* タイトルには具体的な変更対象とアクションを記載する。

* コードから容易に判断できる実装手順は書かない。

* 自明な背景説明、一般論、重複表現を省略する。

* 完了条件は重要なものに絞り、検証可能な形で記述する。

* 複数の独立した作業が混在し、読みづらい場合は子Issueに分割する。

* 子Issueは親Issueの説明を繰り返さず、固有の作業内容のみ記述する。

* 詳細な調査結果や技術的な議論は、必要に応じてコメントや関連ドキュメントへ分離する。

* Issueを短くするために、重要な制約や完了条件を省略してはならない。
